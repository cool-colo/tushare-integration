# ≥1% 复权因子问题的源端复核

本次确认 22 只股票、9,595 个股票/日期的本地最新因子与当前 Tushare 相差至少 1%。问题表现为旧历史未跟随源端修订，同一条时间序列拼接了不同观测版本。小于 1% 的差异暂时跳过；本次没有删除、补写数据库，没有重建 DWD，也没有用米筐替换 Tushare。

这里的“确认”是确认本地/当前同源差异及其具体日期，不能据此保证当前 Tushare 的公司行动、累计基准绝对正确。米筐用于筛选异常变化，当前 Tushare 用于核定同源修订；两者原值均保留。

## 定位到的代码行为与影响

[DailySpider.start_requests](/data/flc/code/quant/tushare-integration/tushare_integration/spiders/tushare.py:332) 使用已有日期的 NOT IN 查询，只请求尚未存在的日期。即使设置了回溯天数，日期已经存在仍会跳过，所以不能自动收敛源端对旧日期的修订。adj_factor 的日常采集不计算复权因子；69 个异常端点的原始 JSON、raw 数值及最新表数值全部一致，未发现这些样本的数值转换错误。

此前已核对，周六全量任务也不重新拉取 adj_factor；重建 DWD 只会再次使用当前本地值，无法修复上述同源差异。根因可定位为“历史修订未刷新，序列混用了不同观测版本”；不能把全部差异归因于本地算错，也不能仅凭现有响应确认 Tushare 内部修订原因或准确发生时间。

相同的累计基准倍率不一定影响区间收益，但不同历史版本的边界会影响复权价及跨边界收益。这里优先处理的是已确认出现异常衔接且当前源端历史不同的股票，未把所有 ≥1% 的跨源累计因子差异都判为 bug。因子也不能被无条件要求单调递增。

本次优先查异常变化，并未逐只向当前源端展开此前全部 557 只“绝对跨源差异 ≥1%”股票。因此 22 只、9,595 日期是本次已确认范围，不是全市场问题的上限。

## 修复方式

按 [repair_dates_ge_1pct.csv](repair_dates_ge_1pct.csv) 的股票及日期，通过已有 run replay stock/quotes/adj_factor 命令补采，每只股票显式传 --ts-code 和重复的 --trade-date。只重新请求清单中的同源数据；写入时保留新观测批次与时间，不抹掉旧 raw 观测。

补采完成后重新核对最新表、raw 批次与当前源端，并核查版本边界处的跳变。源端为空、失败或响应完整性不能确定时不覆盖现有数据。DWD 继续按用户要求暂不重建。

要避免复发，需要让 adj_factor 的历史刷新能覆盖已经存在的业务日期，并给较早的公司行动修订保留专项补采途径。仅重建下游或修改“回溯天数”而继续跳过已有日期，不能解决根因。本次没有改每日/每周任务。

600610.SH 当前 Tushare 的 72.136 仍与米筐 58.344 不同，000545.SZ、600717.SH 等也存在修订后跨源差异。补采解决同一来源的新旧版本衔接；这些跨源口径差异仍需独立核查，不能自动择源或互相替换。
