## 最终实现

`DWSManager` 恢复全市场、全历史的一条完整 SQL，1968 列同时写入唯一候选表，没有物理中间阶段表。移除阶段构建、资格报告和阶段重启接口。隔离试建入口为 `scripts/build_v2_single.py`；正常 `dws sync` 仍在校验后原子交换，旧正式数据保留在此次候选名称下，交换失败停止，不使用删表降级。

| 新增字段分支 | 在展开前限制输入的方法 | 必须保留的业务边界 |
|---|---|---|
| 研报覆盖、机构年度对计数、目标价 | 股票＋报告月份等值 JOIN，交易日最多生成 4 个月份键，再执行精确 90 日条件 | 先选每篇可见版本，再判断目标价区间有效性；无输入不补零 |
| 年度预测、active 预测、净资产预测 | 源侧形成机构／绝对预测年度可见状态，再按交易日必要年度 ASOF | 必要年度为 FY0..FY3、CY/CY+1、正权重净资产投影年及 active 年；长预测无统一年龄过期；180/90/91 日窗口及机构门槛保持 |
| 近 12 月分红与留存率分红 | 股票＋除息年度等值 JOIN，保留近 12 月涉及年度与留存率需要的 3 年，再执行精确日期和版本条件 | 版本选择后过滤实施与金额；留存率输入不能只保留 12 月；每股税前分红×万股基数×10000 |
| 财政年度、年度实际净利润 | 源侧按披露状态日期计算最新报告期、最新年度及精确前两年，再 ASOF 匹配交易日 | 旧期晚到修订不替代更新业务期；缺失年报不补取更老年度；最新 NULL 保持 NULL |
| 最新归母净资产 | 源侧建立最新业务报告期状态，再 ASOF | 不改变可用日及合并报告版本优先级 |
| 新增半年折旧 | 新增辅助读者仅保留 6/12 月，源侧计算最新半年期及同年 6 月基数，再 ASOF | 原 MRQ／TTM／LYR 财务链路完整保留；各财务表使用自己的可用日 |
| 中证 800 成员 | 全指数最新完整快照状态 ASOF | 个股试建不裁剪指数来源；无完整性证据不输出 0 |

只移动混合日期条件到 `JOIN ON` 不一定减少 JOIN 内部展开。实际 EXPLAIN 已确认研报使用股票＋月份键、分红使用股票＋年度键，见 [研报计划](../../logs/v2-research-visible-explain-20261125.txt)、[分红计划](../../logs/v2-dividend-events-explain-20261125.txt)。分红证据文件中的财务部分生成于源侧状态优化前；上述键及日期逻辑保持一致。

不改字段来源、单位、财报窗口、NULL 语义，也不添加跨数据源补齐。经确认，来源批次和哈希改为实际依赖：目标价选中记录纳入血缘，零权重净资产预测年度不纳入血缘。因此血缘批次、哈希和构建时间不能与旧版要求逐字一致。

构建默认 `warn_only`，可显式 `strict`，V2 不允许跳过校验。源表 UUID、字段定义与活跃物理分片在构建前后核对；任何变化停止发布并保留候选，后台合并也会触发此保守检查。

## 后续性能方向与交付边界

本次运行的 CPU 堆栈大量停留在 `DB::Context::addQueryFactoriesInfo`，路径为 `NativeReader::read` → `DataTypeFactory::getImpl` → 记录类型工厂信息，见 [堆栈证据](../../logs/v2-single-full-factory-stacks-20261125.jsonl)。ClickHouse 对应版本的 [DataTypeFactory 源码](https://github.com/ClickHouse/ClickHouse/blob/v25.8.22.28-lts/src/DataTypes/DataTypeFactory.cpp#L147) 和 [Context 源码](https://github.com/ClickHouse/ClickHouse/blob/v25.8.22.28-lts/src/Interpreters/Context.cpp#L2424) 确认该路径在 `log_queries=1` 时取得查询上下文中的互斥锁并插入完整类型名；`log_query_settings=0` 不会关闭它。1968 列外部数据块反复反序列化带来类型解析与锁开销，可后续评估类型缓存或 ClickHouse 版本修复；本次未修改服务端、关闭查询日志或改变运行中 SQL。

用户询问提高到 200 MiB/s 的收益：写入阶段一次 25.09 秒采样中，压缩文件写入增加 103595052 B（约 3.94 MiB/s），读限速字节与读／总限速等待未增加，见 [采样记录](../../logs/v2-single-bandwidth-observations-20261125.jsonl)。这个短区间没有达到 100 MiB/s，不能预期提高带宽直接使该阶段翻倍；此前外部数据回读确有累计限速等待，提高带宽可能帮助部分阶段。等待指标汇总多个线程，不能除以查询墙钟时间当作可削减比例；未通过另一次 200 MiB/s 全量构建测得总收益。本次限速保持 100 MiB/s。
